# SNS Notification Fan-Out — Architecture

Companion guide for `sns-notification-fan-out.drawio`.

Reflects the actual CDK stack in `cdk/lib/fanning-sns-stack.ts`. This stack was
generated by `cdk migrate --from-stack` against the live CloudFormation template, then
hand-cleaned — for `stage: 'prod'`, every logical ID and physical name matches the
originally-deployed (SAM-created) stack exactly, so `cdk deploy` is a normal in-place
update, not an import.

## Flow

1. **Website Visitor** calls **Amazon API Gateway** `POST /notify`. The
   `PublisherFunction` Lambda publishes the message to an **Amazon SNS** topic
   (`NotificationTopic`).
2. The topic fans out to **two independent subscribers**:
   - **Direct Lambda subscription**: `NotifierFunction` runs immediately, sends an
     email via **Amazon SES**, and writes a delivery-log row to **Amazon DynamoDB**.
   - **SQS subscription**: messages queue in `LoggerQueue`, which triggers
     `LoggerFunction` (via an event source mapping, batch size 5) to also write a
     delivery-log row — demonstrating the fan-out pattern's two different consumption
     styles (synchronous push vs. buffered pull) side by side.
3. `GET /notify/recent` (via `RecentFunction`) reads recent delivery-log rows back for
   the frontend, using a `RecentIndex` GSI on the shared `DeliveryLogTable`.
4. **Dead-letter monitoring** (not shown in the diagram): `LoggerQueue` redrives to a
   `LoggerDLQ` after 3 failed attempts. A CloudWatch alarm watches the DLQ's
   `ApproximateAgeOfOldestMessage` metric and fires (re-evaluating every 6 hours) once
   a message is 2+ days from its 4-day retention limit, publishing to a separate SNS
   topic that invokes `DlqAlertFunction`, which emails a warning via SES before the
   message would otherwise silently expire.

## Services

| Service | Role |
|---|---|
| Amazon API Gateway | HTTP API for publish and recent-history reads |
| AWS Lambda | Publisher, notifier, logger, recent-reads, and DLQ-alert handlers |
| Amazon SNS | `NotificationTopic` (main fan-out) and a separate DLQ-age alert topic |
| Amazon SQS | `LoggerQueue` (buffered subscriber) with a dead-letter queue |
| Amazon SES | Notification emails and DLQ-age warning emails |
| Amazon DynamoDB | `DeliveryLogTable`, written by both fan-out consumers |
| Amazon CloudWatch | Alarm on the DLQ's oldest-message age |

## Key design decisions

- **Two subscribers on one topic, on purpose.** Direct-Lambda and SQS-buffered
  subscriptions are both wired to the same topic specifically to show the pattern's
  two consumption styles side by side, not because the demo needs both for its own
  sake.
- **The DLQ is actively monitored, not just a retention backstop.** A message that
  fails 3 times used to just sit until its 4-day retention silently deleted it —
  nothing consumed or watched the queue. The age-based alarm now gives 2 days' notice
  before that happens.
- **Prod resources are retained, beta's are disposable.** Prod's table keeps
  `RemovalPolicy.RETAIN` (imported holding real data); beta's fresh resources use
  `DESTROY`.
