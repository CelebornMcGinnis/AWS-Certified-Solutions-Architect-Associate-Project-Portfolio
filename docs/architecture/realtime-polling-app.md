# Movie Poll — Architecture

Companion guide for `realtime-polling-app.drawio`.

Reflects the actual CDK stack in `cdk/lib/live-poll-stack.ts`. Generated by
`cdk migrate --from-stack` against the live CloudFormation template, then
hand-cleaned — for `stage: 'prod'`, every logical ID and physical name matches the
originally-deployed (SAM-created) stack exactly.

## Flow

1. **Website Visitor** opens a **WebSocket API** connection. The `$connect` route
   invokes `PollConnectFunction`, which writes a row to `PollConnectionsTable`.
2. On `vote` / `sync` routes, `PollVoteFunction` writes to `PollVotesTable` (one row
   per voter per poll — a conditional key prevents double-voting) and updates the
   running count in a separate `PollTalliesTable`. It then uses
   `execute-api:ManageConnections` to **broadcast the updated tallies to every open
   connection** in `PollConnectionsTable`, not just the voter who just voted.
3. On `$disconnect`, `PollDisconnectFunction` removes the connection row **and sends a
   lifecycle email via Amazon SES** — the diagram's "Notify" edge comes from
   disconnect, not connect.

The diagram simplifies the three separate tables (connections, votes, tallies) to one
"Connections / Votes" node for readability, and shows the notify path from the connect
Lambda rather than disconnect.

## Services

| Service | Role |
|---|---|
| Amazon API Gateway | WebSocket API (`$connect`/`$disconnect`/`vote`/`sync` routes) |
| AWS Lambda | Connect, disconnect (+SES), and vote (+broadcast) handlers |
| Amazon DynamoDB | Separate `PollConnectionsTable`, `PollVotesTable`, `PollTalliesTable` |
| Amazon SES | Lifecycle email sent on disconnect |

## Key design decisions

- **Voting broadcasts to every connection, not just the voter.** `PollVoteFunction`'s
  IAM policy is scoped to `execute-api:ManageConnections` on this API's `POST
  /@connections/*` route specifically, so it can push to any open connection.
- **A conditional put on votes prevents double-voting** per `pollId`/`voterId` pair,
  enforced at the DynamoDB layer rather than trusted to client-side logic.
- **Beta seeds starting vote counts via a one-time custom resource.** `onCreate` only
  (no `onUpdate`), with an `attribute_not_exists` condition as a second safety net —
  so it can never clobber real demo votes that accumulate after the table is first
  created, and later `cdk deploy` runs leave it alone.
- **Prod tables are retained, beta's are disposable.** Prod's tables keep
  `RemovalPolicy.RETAIN` (imported holding real data); beta's fresh tables use
  `DESTROY`.
